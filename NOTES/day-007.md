# 🧠 What I Learned

## Lottery
- Two locks are not better than one when one hides a bug: `restricted` on both `resetPlayers()` and `pickWinner()` kept the test green even after removing it from `pickWinner()`. Removing the redundant lock and re-running the sabotage showed the test now fails for the right reason.
- Empty `players` gives a modulo-by-zero panic; a `require(players.length > 0, ...)` gives a clear message.

## Bank
- Balances live in a `mapping(address => uint256)`, not a struct (one value per address).
- `withdraw(amount)` pattern: check (`require(amount <= soldes[msg.sender])`) → effect (`soldes[msg.sender] -= amount`) → interaction (`call{value: amount}`, then `require(success)`).
- A first version used `transfer(address(this).balance)` before updating the balance: any depositor could withdraw the whole contract balance (critical bug: other users' funds stolen, their ledger entries unbacked).
- `transfer` forwards 2300 gas, enough for a normal wallet but a problem for contract receivers. `call` forwards all gas and is the modern way, but it enables reentrancy if state is updated after the call.

## Reentrancy (concept)
- An attacker contract's `receive` function calls `withdraw()` again before the first call finished. If the balance was not reduced yet, the `require` passes again and again.
- Defence: update state before sending ETH (checks-effects-interactions).
- Not yet demonstrated in code: next session.

## Tests
- Bank test 4 ("detect a vulnerability"): Alice deposits 10 ETH, Bob deposits 1 and withdraws 1; the contract must still hold 10 ETH. Sabotaged `withdraw()` with `address(this).balance` and both the withdraw test and this test turned red, for the right reason (contract balance 0).
- Hardhat quirk in the Bank project: `npx hardhat test` without argument failed with `Invalid Chai property: revertedWith` while `npx hardhat test test/bank.test.js` passed. Adding `require("@nomicfoundation/hardhat-chai-matchers");` at the top of the test file fixed it. Root cause not identified.
