# 🧠 What I Learned

## Bytecode vs ABI, revisited

Solidity source code is compiled into two artifacts:

- **Bytecode** — what actually gets deployed and executed by the EVM. The EVM never sees Solidity, only bytecode.
- **ABI** — not executable. It's the interface description that tells an external application (a frontend, ethers.js, etc.) what functions exist, what arguments they take, and how to encode/decode calls to the deployed bytecode.

Mental model: Bytecode is the contract's body running on-chain. The ABI is the instruction manual for talking to it from outside.

## call() vs send()

- `call()` — reads contract state. No transaction is created, no gas is spent (from the caller's perspective), state is unchanged. Used for `view`/`pure`-style reads.
- `send()` — creates an actual transaction. Costs gas, gets mined into a block, and can change contract state.

This is the practical version of "reading the blockchain is free, writing to it costs money."

## Sepolia deployment

Deployed a contract to the Sepolia testnet (public, but not mainnet — no real ETH at risk) instead of only testing locally. This is the first time the contract had a persistent public address visible on Etherscan, with real transaction history instead of a throwaway local instance.

# 💡 Biggest Lesson Today

Every concept builds on the last one: the mempool/transaction model from Day 1 is what actually gives `send()` its cost and delay, while the Bytecode/ABI split from earlier lessons is what makes `call()`/`send()` even possible from a frontend. Deploying to Sepolia made the "developer → Solidity → compiler → bytecode+ABI → deploy → address → ethers.js → frontend" pipeline (from Day 1's mental model) concrete for the first time instead of theoretical.
